# 미로 탈출 — 협동 게임 프로토타입

Babylon.js + TypeScript 로 만든 호스트 권위형(host-authoritative) 협동 미로 탈출 게임.
스팀 배포를 전제로, 전송 계층만 갈아끼우면 Steam P2P 로 넘어갈 수 있게 설계했다.

**흐름**: 로비(일반 방)에서 시작한다. 상점에서 아이템을 사고, 던전 구멍으로 들어가면
설정한 레벨을 1층부터 차례로 돈다. 각 층은 열쇠를 모두 모아 탈출구를 열고 팀원 전원이
탈출하면 클리어. 마지막 층을 깨면 골드와 아이템을 유지한 채 로비로 돌아온다.

미로 안에는 사각형 방이 뚫려 있다. 균일한 통로만 있으면 어디가 어딘지 구분이 안 되고
"저 방에서 만나자" 같은 약속을 할 수가 없어서, 넓은 공간을 이정표로 둔다.

## 빠르게 실행

```bash
npm install
npm run dev          # http://localhost:5173
```

실행하면 먼저 **설정 화면**이 뜬다. 레벨을 원하는 만큼 추가하고 각 레벨의
미로 가로·세로, 방 개수, 열쇠 개수를 정한 뒤 시작한다. 설정은 브라우저에 저장돼서
새로고침해도 유지된다.

기본은 인프로세스 모드다. 한 페이지 안에서 호스트와 클라이언트가 함께 돌기 때문에
네트워크도, 서버도 필요 없다.

| URL | 용도 |
| --- | --- |
| `/` | 설정 화면부터 시작 |
| `/?skipSetup=1` | 저장된 설정으로 바로 시작 |
| `/?views=4` | 한 화면에 클라이언트 4명. 네트코드 눈으로 확인 |
| `/?views=4&lat=120&jitter=30&loss=0.05` | 지연 120ms · 지터 30ms · 손실 5% 주입 |
| `/?ws=ws://192.168.0.10:8080` | 실제 WebSocket 호스트에 접속 |

**조작**: `WASD` 이동 · `F` 상호작용(던전 입장) · `V` 시점 전환(좌상단 버튼으로도 가능)

시점 회전은 환경에 따라 두 방식으로 동작한다.
- 일반 브라우저: 화면을 클릭하면 Pointer Lock 이 걸리고 마우스로 자유롭게 돌린다.
- 샌드박스 iframe(Artifact 뷰어 등): Pointer Lock 이 permissions policy 로 막히므로,
  **누른 채 드래그**하면 돌아간다. `Q` / `E` 로도 좌우 회전이 가능하다.

**디버그 패널** (우상단, 네트워크 패널 아래)
- 미니맵 전체 보기 — 탐사 여부와 무관하게 미로 전체를 표시
- 미니맵 크게 보기 (`M`) — 화면 중앙에 크게 띄운다
- 방 강조 표시 / FPS · 미로 크기 · 방 개수

실제로 두 대 이상 붙여보려면 호스트에서:

```bash
npm run server       # ws://0.0.0.0:8080
```

## 구조

```
src/
  shared/     게임 로직. 렌더링·입력·전송에 대한 의존이 전혀 없다
    config.ts   런 설정(레벨 목록). 미로 크기·방·열쇠 개수를 데이터로 뺐다
    items.ts    아이템 정의와 효과. 효과 계산이 호스트/클라 공용이어야 한다
    maze.ts     시드 기반 미로 생성 + 충돌 + 로비 생성
    sim.ts      권위 시뮬레이션 (로비/던전 존, 재화, 상점)
    protocol.ts 바이너리 직렬화
  net/        전송 계층
    transport.ts  인터페이스
    in-process.ts 같은 프로세스 안에서 연결. 지연/지터/손실 주입 가능
    websocket.ts  로컬 실기기 테스트용
    steam.ts      Steam P2P 스텁 (Electron 붙일 때 채운다)
  game/
    host.ts         호스트 틱 루프
    client-state.ts 예측 · 보정 · 스냅샷 보간
  client/     Babylon 렌더링, 카메라, 미니맵, HUD
  server/     WebSocket 호스트
```

## 아이템 · 재화

로비 상점에서 골드로 산다. 시작 골드 100, 레벨 클리어마다 보상.
아이템은 "가지고 있냐"만 관리해서(비트마스크) 스냅샷에 1바이트로 들어간다.

| 아이템 | 가격 | 효과 |
| --- | --- | --- |
| 신속의 장화 | 60 | 이동 속도 +20% |
| 랜턴 | 45 | 시야가 넓어지고 미니맵이 한 칸 더 열린다 |
| 나침반 | 80 | 안 가본 곳의 열쇠도 미니맵에 보인다 |
| 열쇠 감각 | 35 | 가장 가까운 열쇠까지의 거리 |

효과 계산(`moveSpeedFor` 등)은 반드시 `shared/items.ts` 한 곳에만 둔다.
이동 속도가 아이템에 좌우되므로, 클라이언트 예측이 호스트와 다른 값을 쓰면
아이템을 산 순간부터 예측이 계속 어긋난다.

## 설계 메모

**호스트 권위형.** 시뮬레이션은 호스트에서만 돈다. 치팅 방어가 필요 없는 협동 게임이라
결정론도, 서버 재검증도, 롤백도 필요 없다. 클라이언트는 입력을 보내고 스냅샷을 받는다.

**미로는 전송하지 않는다.** 런 설정 + 시드만 보내면 각자 같은 미로를 만든다.
`generateMaze` 가 결정론적이라는 게 전제 조건이고, 테스트로 고정해 뒀다.

**로비도 Maze 구조를 재사용한다.** 충돌·렌더링·미니맵·카메라 벽 회피가 전부 Maze 기준으로
돌기 때문에, 로비를 별도 타입으로 만들면 그 코드를 두 벌로 관리해야 한다.
로비는 "내부 벽이 전부 없는 미로"일 뿐이다.

**열쇠 배치에는 최소 거리 조건이 있다.** 점수 높은 순으로만 뽑으면 열쇠가 한 곳에 뭉치고
탈출구 바로 옆에 놓이기도 해서, 미로를 돌아다닐 이유가 사라진다. 스폰에서·탈출구에서·
열쇠끼리 각각 미로 지름 대비 비율로 최소 거리를 건다. 조건을 만족하는 칸이 부족하면
조금씩 완화하며 재시도하고, 끝내 안 되면 조건 없이 채운다 — 열쇠가 하나라도 모자라면
탈출구가 영영 안 열려서 진행 불가가 되기 때문이다.

**클라이언트 예측은 호스트와 같은 고정 스텝(20Hz)으로 돈다.**
프레임 단위로 적분하면 직선 구간은 같지만 벽을 스치며 미끄러질 때 결과가 갈라진다.
화면은 스텝 사이를 보간해 60fps 로 그린다.

**보정은 시간 기준으로 감쇠시킨다.** "프레임당 몇 %" 로 잡으면 60fps 기기와 20fps 기기의
보정 속도가 3배 차이 난다. 또한 매 스냅샷의 오차는 이미 이전 보정이 반영된 잔차이므로,
누적하지 않고 대입해야 한다 (누적하면 과보정 → 진동).

**원격 플레이어는 100ms 지연시켜 그린다.** 최신 스냅샷을 바로 쓰면 패킷 간격이
흔들릴 때마다 캐릭터가 떤다.

**3인칭 카메라의 벽 회피는 연속값이어야 한다.** 성긴 격자로 훑으면 거리가 몇 개의
이산값으로 뭉쳐서, 회전할 때 한 프레임에 셀 1/3씩 튄다("화면이 뚝뚝 끊긴다"의 정체).
이분 탐색으로 연속값을 만들고, 당길 때는 빠르게 놓을 때는 천천히 시간 기준으로 따라간다.
수치는 `scripts/camera-probe.mjs` 로 재서 정했다.

**reliable / unreliable 구분.** 입력과 스냅샷은 unreliable(최신 것만 의미 있음),
참가와 레벨 전환은 reliable(놓치면 상태가 영영 어긋남). 스팀의 `SendType` 과 그대로 대응된다.

**스냅샷은 1200바이트 안에 들어간다.** 스팀 P2P Unreliable 패킷의 상한이다.
정원 4명 기준 실제로는 100바이트 안쪽이고, 상한 초과는 테스트로 막아 뒀다.

## 테스트

```bash
npm test                       # 로직 + 네트코드 통합 (64개)
npm run smoke                  # 헤드리스 브라우저 실동작 검증 + 스크린샷
npm run verify:artifact        # 단일 HTML 배포본이 외부 요청 없이 도는지 확인
npx tsx scripts/camera-probe.mjs   # 3인칭 카메라 부드러움 계측
```

`npm test` 는 브라우저 없이 실제 `GameHost` + `GameClientState` 를 `InProcessHub` 로
연결해 돌린다. 렌더링만 빠졌을 뿐 참가·예측·보간·보정이 전부 동작한다.

`npm run smoke` 는 실제 Chromium 에서 번들이 뜨는지, Babylon 트리셰이킹에서
사이드이펙트 임포트를 빠뜨리지 않았는지, 키 입력이 캐릭터를 움직이는지를 본다.
결과 스크린샷은 `screenshots/` 에 남는다.

## 스팀으로 옮길 때

게임 로직과 `GameHost` 는 그대로 두고 `HostTransport` / `ClientTransport` 구현만 바꾸면 된다.
`src/net/steam.ts` 에 `steamworks.js` API 대응이 주석으로 정리돼 있다.

로비 주인이 곧 호스트가 되고, `LobbyType.FriendsOnly` 로 만들면 스팀 친구 초대가
그대로 방 참여 경로가 된다. 릴레이(SDR)를 타므로 NAT 통과는 신경 쓸 필요가 없다.

**먼저 확인할 것 하나** — Electron 과 스팀 오버레이는 지금도 궁합이 나쁘다.
Chromium 이 매 프레임 화면을 갱신하지 않으면 오버레이가 얼거나 깨지고,
Electron 버전에 따라 아예 동작하지 않는 회귀가 보고돼 있다.
오버레이가 친구 초대 UI 이기도 하므로, **게임을 다 만들기 전에 최소 빌드로 먼저 검증**해야 한다.
